# 方案提出与评估

适用条件：提出或评估方案、整理供执行的流程，或依据用户纠正修订这类回答。先形成方案，再按下列步骤检查；检查工作由 Agent 主动完成。

## 1. 核对目标与依据

- 明确用户要达到的状态、完成条件和已确认约束，按当前任务范围判断。将这些要求与已有实现、待验证假设分开；说明哪些事实会改变推荐或执行结果。
- 从当前对话及获准访问的相关材料中核对既有决定。整理已有流程时，保留影响执行的约定、分工和例外；资料间有差异时说明来源与适用范围。
- 对影响方案的未知信息，先自行查证可获取的部分；仍需用户决定的事项，说明具体影响并给出推荐。用户明确要求重新评估的既有做法按评估对象处理；其余已确认约束和授权继续有效。

完成条件：能将方案的目标、关键约束和待核实项对应到实际依据；由此判断后续步骤是否足够。

## 2. 检查完整流程

- 从用户实际起点推演到完成状态，核对必要前提、执行顺序、每步执行方、所需输入、触发方式、产出及下一步如何使用它。检查范围以会影响目标达成的条件为准。
- 涉及多个主体、系统或设备时，检查每次交接：内容由谁产生、采用依据由谁确定、如何到达下一方，以及接收方何时实际使用。存在多个来源、版本或本地改动时，明确选择和冲突处理依据。
- 对会改变结果的中断、失败或前提不成立，说明如何识别及接续。用实际结果的验证方式结束流程，分别判断中间步骤成功和目标达成。

完成条件：从起点到结果的关键步骤都有可执行的衔接；尚缺的机制、实现或外部依赖有明确位置及影响，不将依赖未满足的方案写成已经可用。

## 3. 检查实现依据

- 从完成条件确定所需能力或证据，再判断现有或拟用机制是否必要、是否适合。分别给出“目标是否需要满足”和“采用这个具体机制是否合适”的判断及依据；不能只论证前者就推荐后者。
- 需要选择实现时，先识别决定方案路径的核心机制，检查去掉或替换它后能否满足同一完成条件。比较能够替代该机制的合理路径，或说明使它不可替代的具体约束；把同一路线内的脚本封装、参数调整等实现优化放在路线选择之后。结合复杂度、成本、可靠性及证据覆盖给出推荐，不编造候选凑数。实现选择遵守全局主指令对用户明确约束和知情选择的要求。
- 候选依赖的能力尚未核实时，先给出条件性比较、推荐和需核实项，完成当前可做的评估；已有方案的来源不作为延后比较的依据。区分资料记载、当前查证、推断和待实现能力，说明验证结果覆盖的范围。

完成条件：目标的必要性与核心机制的选择分别有依据；能替代核心机制的合理路径已主动比较，或已说明排除它们的具体约束；关键代价及仍影响选择的不确定性已说明。

## 4. 收到纠正后复查

- 核对纠正涉及的是已有信息遗漏、原有论证不足、新事实还是目标/约束变化，按证据说明本次修订依据。
- 重新检查受影响的前提、上下游步骤和依赖原判断的结论；修正关联配置、职责及完成条件，保留仍成立的部分。
- 给出连贯的修订方案，并指出仍未核实的关键部分。补上用户指出的内容后，还须完成上述相关检查；不把补充一项或接受建议视为整体已充分验证。

## 回答与验证

按任务复杂度呈现目标、关键流程、推荐依据和未解决依赖。评估关键实现时，回答须呈现核心机制及替代路径的比较结论，或使其不可替代的具体约束。篇幅以支持用户判断及下一步行动为准，无需逐项展示检查表或内部推理。整理历史与提出新建议分别标明。检查发现的问题应体现在修订后的内容中，不能用“已全面考虑”代替依据。

方案论证、实际实施及结果验收分别报告。指令写入、加载成功或少量案例通过，只能证明相应范围；规则效果以正常输入下的实际行为验证。
