# 开发中的关联功能评估

适用条件：设计、开发新功能或修改已有功能前。Agent 在设计阶段主动完成以下评估；实现中发现新的关联或前提变化时，复查受影响的判断。

## 1. 查清关联与原有用途

- 从本次目标、职责、数据和操作流程出发，查阅相关设计依据、规则与实现。检查上下游调用、共享配置和数据，也查找职责相近或可能被新方案替代的既有机制；没有直接代码引用的功能，也按实际职责和流程关系纳入检查。
- 核对关联功能原来解决的问题、当前使用方及独立用途，分别判断当前实现有哪些依赖、目标仍然需要哪些能力。检查范围以本次变更的实际关联为界。

完成条件：能说明相关功能与本次变更的关系、原有用途及依据；尚未查清的用途或依赖有明确位置。

## 2. 评估必要性、优化机会与必要调整

对识别出的关联功能检查以下三个方面；同一功能可以同时涉及多个方面。

| 评估方面 | 要回答的问题 |
| --- | --- |
| 必要性 | 原有职责是否仍需保留，新方案是否已承担这些职责；应当保留、合并、简化还是取消哪些功能或实现机制？ |
| 优化机会 | 仍需保留的功能，能否借助本次变化改善使用体验、性能、可靠性或维护成本；具体收益与代价是什么？ |
| 必要调整 | 本次变化是否改变其他功能依赖的前提、接口、数据、配置或流程；哪些地方必须配套修改，不调整会造成什么问题？ |

提出合并、简化或取消前，核实新方案对原有职责的覆盖，以及其他使用方和独立用途；把尚未解除的依赖列入配套调整。证据不足时给出条件性判断与待核实项，区分“职责可以由新方案接替”和“现有依赖已经解除”。

完成条件：关联功能的保留或调整建议有具体依据；可选优化与必须调整已区分，仍然适用的部分可以保留原状。

## 3. 主动告知并纳入方案

- 在设计阶段向用户说明会影响方案或实施范围的发现：具体对象、判断依据、建议、收益与代价，以及不调整的后果。主动提出相关功能可以优化、需要调整或可以退出的部分，无需等待用户逐项指出。
- 将必要配套调整纳入实施与验收范围，在既有授权内一并完成。可选优化是否实施，依据本次目标与授权确定；涉及尚未确定的方案取舍时，说明影响并给出推荐，由用户决定，已有明确选择和授权继续有效。

完成条件：方案已覆盖必要调整，并说明可选优化及待定取舍；依赖尚未解决的部分有明确影响与后续动作。

## 4. 实现中复查并验证关联结果

- 根据实际影响同步调整代码、配置、脚本、规则、文档及迁移安排。实现中发现新依赖、新用途或前提变化时，更新相关判断和方案，及时说明影响。
- 从受影响的实际入口验证新功能与关联功能能共同完成目标，核对必要调整及适用的迁移结果。按实际影响选择验证范围。

完成条件：报告已完成的关联调整、验证结果及剩余缺口；尚缺必要调整或关键验证时，明确未完成范围，不以单个新功能可运行代替整项完成。
