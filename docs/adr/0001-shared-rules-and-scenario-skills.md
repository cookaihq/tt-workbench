# 集中维护本库规则，并按使用场景组织 Skill

本库的共同规则集中维护，由工作台、Skill、模板和其他录入工具依据规则实现功能。Skill 围绕实际使用仓库的场景组织，在后续使用中逐步调整；Plugin 用于能力的成套安装与管理，其是否立即引入及具体实现另行确定。现有 `tannt-save-note` 的结构和接口调用方式不再是新设计必须兼容的前提。

## 背景与范围

当前工作台仍处于初始阶段。现有保存 Skill 将 Agent 的保存操作绑定到运行中的工作台接口，笔记规则、接口限制和实现说明也分散在多处。已经完成的技术接入与部分读写验证，不足以证明该 Skill 的使用流程合理，不能据此将它作为后续设计应当沿用的先例。

本次目标是确定当前 `tannt` 库的规则维护方式，以及规则、Skill 和工作台实现之间的关系。适用对象包括本库的共同规则、Agent 工作流程、工作台、模板、脚本和其他录入工具，不扩展到私人库或其他仓库。

“Agent 首轮回答遗漏信息”是另一项问题，不属于本 ADR 的目标或验收范围。

## 已接受的决策

### 1. 先确定规则，再设计实现

先确定内容如何组织、保存、读取和更新，再选择实现方式。工作台当前不支持某项操作，表示实现能力尚未满足相应要求，不能自动转化为整个笔记库的业务限制。实现中发现规则存在不可行之处或冲突时，应提供依据并重新讨论规则，不能静默修改规则含义。

重新设计现有保存 Skill，不以兼容其结构、名称或接口调用方式为前提，也不预设工作台接口是所有 Agent 操作的唯一入口。具体采用文件操作还是接口，在相应使用场景中按已确认规则、实际能力与验证结果选择。

Agent 的运行及本库业务文件操作不得要求 Obsidian 打开当前库。读取、新建、追加、属性更新和附件保存都必须有独立于运行中 Obsidian 与工作台插件的执行方式；不能只解除新建的依赖，却把修改已有笔记排除在外。目标库通过实际路径确认，文件访问权限和本次操作授权仍须核对；不能把取得工作台连接信息作为确认目标库的唯一方式。

Obsidian 未启动、当前库未打开或工作台插件未运行，均不能单独构成 Agent 业务操作的阻塞理由。不得要求用户打开或切换到当前库来满足保存前置条件。工作台打开后读取同一份业务文件；界面显示与重新加载的验收另行进行，不成为每次 Agent 操作报告文件写入结果的条件。并发修改仍须设计和验证，但不能通过重新要求 Obsidian 运行来回避独立更新能力的实现。

### 2. 共同规则正文集中维护

共同规则正文放在 `docs/rules/`，按主题组织。同一规则只有一处正文，其他位置保留必要摘要和引用，不维护可以独立修改的副本。

| 位置 | 职责 |
| --- | --- |
| `docs/rules/` | 本库共同规则，包括目录与命名、笔记格式、来源与附件、状态及操作边界 |
| `AGENTS.md` | 说明 Agent 在什么情况下必须读取哪些规则，并提供执行入口 |
| `docs/agents/`、各 `SKILL.md` | Agent 完成具体任务的执行流程，引用适用的共同规则 |
| `docs/workbench/` | 工作台如何实现规则、当前能力、使用说明及未完成项 |
| 工作台代码、模板和脚本 | 实际执行规则，并接受相应验证 |
| `docs/adr/` | 记录重要设计决定及其依据，不复制各项日常规则正文 |

迁移前逐项区分已确认的业务规则、具体实现限制和未确认提案，不把现有文档全部直接认定为正式规则。已有规则迁移后更新原位置的引用，避免新旧正文并存。术语定义继续按本库领域文档约定维护，本决策不改变已有业务概念。

Skill 使用目标库的规则；如果 Plugin 安装目录与目标库分离，应先确认目标库，再按目标库根目录解析规则路径，不能把插件安装目录当作笔记库。

### 3. Skill 按使用场景逐步组织

从实际使用仓库的场景发现需求，再根据输入、执行步骤和完成标准确定 Skill 边界。步骤相近的场景可以共用一个 Skill，复杂场景可以组合多个 Skill，不固定要求场景与 Skill 一一对应。

本轮提出的候选场景包括创建任务、向收件箱添加内容、创建项目、根据提供的资料整理经验。这些仅为场景示例，不是最终清单，也不据此立即建立完整的 Skill 分类体系。具体流程仍需遵守相应内容的来源、归属和操作规则。

先支持已经明确需要的场景，再根据实际需求和使用结果新增、拆分、合并或修改 Skill。每个 Skill 说明自身的触发条件、输入、执行步骤和完成标准，并引用共同规则；Skill 的拆分不产生另一份共同规则。

### 4. Plugin 的职责与 Skill 划分分别决定

Plugin 用于将相关能力作为一套进行安装、启用和维护。是否立即引入 Plugin、如何打包以及支持哪些 Agent 环境，另行设计和验证。

Plugin 的目录结构不决定使用场景或 Skill 划分，也不要求所有操作通过工作台接口。调整 Skill 的组织方式不必然要求修改工作台，是否需要修改按实际影响判断。

### 5. 规则变更包含受影响实现的同步修改

本人或获授权的维护者确认规则变更后，执行修改的维护者或 Agent 应完成以下流程：

1. 修改共同规则，明确行为变化及用户应得到的结果。
2. 检查受影响的 Skill、模板、脚本、其他录入工具，以及工作台的读取、写入和展示逻辑；同时检查既有笔记能否继续读取。
3. 修改需要调整的实现、引用和相关说明；不受影响的对象说明无需修改的依据。规则文档改变不会自动改变程序行为。
4. 从实际使用入口验证创建、追加、资料保存或状态更新等本次受影响行为，核对真实文件以及适用的工作台展示结果。只修改不影响行为的说明文字时，不要求重跑应用测试。
5. 存在尚未完成的实现或验证时，记录具体缺口，不将整项变更标为完成，也不以旧接口限制替代新规则。

现有 Skill 和接口可以重写；已有笔记如何继续读取、是否需要迁移，根据具体规则变化单独明确，不因重写实现而自动移动或改写既有内容。历史验收保留原有时间与范围，不能用来证明新方案已经通过。

## 取舍与影响

- 沿用现有 Skill 和接口可以减少短期改动，但会把初始实现限制带入新的规则和流程，因此不再把兼容它们作为默认约束。
- 按笔记类别固定划分 Skill 容易把目录分类当成操作流程。采用使用场景作为设计起点，保留随实际使用调整边界的空间，同时需要持续维护触发条件和各 Skill 之间的关系。
- 将规则分别保存在各 Skill 和工作台文档中，单个组件阅读方便，但容易产生多份不同的正文。集中维护减少重复，同时要求引用路径明确、规则变更主动检查各个使用方。
- 接受重新设计和同步修改实现的维护成本；不以当前接口是否方便为标准反推业务规则。
- Agent 的独立读取与写入能力包含更新已有笔记，因此首批实现需要承担相应的文件修改、属性保留和冲突验证成本。现有更新代码的验收可以提供用例，不能证明保留 Obsidian 运行依赖符合本决策。

## 实施状态与待定事项

本决策已接受，用户授权实施的首批 01—04 已完成。共同规则已迁至 [docs/rules/](../rules/README.md)，逐条去向见[迁移记录](../../.scratch/vault-rules-and-skills/rule-migration.md)。独立文件模块、`tt-capture`、`tt-update-note` 与工作台 0.15.0 已安装，模块与真实入口通过；插件关闭、当前库关闭和 Obsidian 完全退出时的独立操作分别通过，重开后的显示与原文件链接已核对。Codex 为已验证宿主，Claude Code 仅标准发现通过；具体支持范围以[实施记录](../../.scratch/vault-rules-and-skills/verification/README.md)为准。

首批通过项目级发现目录接入，不发布 Plugin。后续按实际需要决定创建项目/任务、整理经验等场景的 Skill 边界与 Plugin 打包方式。旧业务文件不批量迁移或重命名；将来具体规则变化需要迁移时单独确定范围。

旧 `tannt-save-note` 已退出活动发现入口，源码目录于 2026-10-21 按本人要求删除。历史验收与本轮实施前的基准归档保留；清单中的退役名称仅用于清理残留安装链接。旧接口不构成兼容要求，它的历史验收不替代新实现验收。其他设备与双电脑 FNS 仍分别核验。
