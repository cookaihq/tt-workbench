## 1. 定位与边界

已经确定：Inbox 接收尚未确定归属的输入，保留当时的内容与上下文，供本人之后阅读和决定如何使用；已经明确属于课程、Project 或 Task 的内容可以直接保存到对应位置。

- 可以记录一句想法、问题、链接、摘录、图片说明或文件引用；不要求先选领域、项目、用途或填写保存理由。
- 一条记录对应一次围绕同一件事保存的内容，可以没有外部来源，也可以包含多个链接、摘录及自己的想法。明确要求“补充刚才那条”时追加，无关内容另建；不将整个 Agent 会话或每条聊天消息机械地当成一条记录。遇到多个无关主题而保存意图不清时，先确认拆分方式。
- “觉得有启发”“可能写成文章”“某个画面值得参考”等想法写在自由文本中。以后若确实需要按某种属性查找，再增加对应字段。
- 已明确属于某门课程、某个 Project 或 Task 的内容，可以直接保存到那里；不要求全部经过 Inbox。
- 保存输入、整理输入、决定投入工作是三件不同的事。前两者不自动创建 Task，也不启动 Agent 执行研究。
- 当前库与私人库继续相互独立。遇到疑似私密内容只提醒，由本人决定后续动作。

Inbox 的“待整理”表示尚未决定怎么保留或使用，不是承诺一定要执行的工作，也没有默认截止日期。

## 2. 内容如何进入仓库：录入入口

本人明确：这里所说的“输入来源”指的是通过什么操作、由哪个程序将内容写入仓库的对应目录；不是在询问文章、视频、课程等内容出处。下文称为“录入入口”，来源出处仍作为笔记内容另行记录。

### 本人提出的四种候选方式

| 入口 | 本人做什么 | 谁创建目录与文件 | 尚需验证或设计 |
| --- | --- | --- | --- |
| 工作台 | 在界面填写内容并保存 | 工作台调用保存程序，按确定的格式创建记录 | 第 02 项已在 Obsidian 插件中用独占文件创建实现真实保存；独立网页未接入，当前 HTML 原型仍不能直接保存到库 |
| 飞书中的 Hermes | 给已接入飞书的 Agent 发消息，要求记录 | Hermes 调用对应 Skill，再由其可访问的保存程序写入库 | 飞书消息进入 Agent 的方式、Agent 的运行设备与库的访问路径、Skill 调用能力，均未在本任务中核验 |
| Obsidian 中的 Claudian 等插件 | 在插件中与 Agent 对话，要求保存内容 | Agent 调用对应 Skill，在当前库创建记录 | 插件当前版本的 Skill／工具调用方式、文件访问范围与运行环境，尚待实际验证 |
| 微信中的 QQClawd／OpenClaw／Workbuddy 路线 | 通过微信对话提交需要保存的内容 | 接入消息的 Agent 调用对应 Skill，然后创建记录 | 保留为本人提出的候选路线；具体组件间如何连接、如何取得附件、在哪台设备执行，尚待核验 |

上述四种方式最初均为接入设想；目前只有工作台文字与链接入口已接通并验收，其他 Agent 路线未验证。其中飞书、微信是本人操作的消息入口，Agent 是执行保存的一方，Skill 规定保存步骤与调用方式。

仓库根目录作为 Agent 工作目录，表示从哪里开始处理文件；仍需明确当前库的实际路径和保存规则。Agent 若运行在其他服务器或容器中，不能直接把本机路径当成该运行环境中存在的路径。应先确认是否有当前库的可写副本，或是否需要向持有当前库的设备提交保存请求。不能假定 FNS 已经提供这种写入接口。

语音听写、截图识别是某个入口取得文字的方式，不需要因此再设计一套独立保存格式。内容出处仍保留：例如从飞书发来的消息可以包含文章链接，也可能只有自己的想法。

### 多个入口共用什么

推荐共用一份保存规范，并让可运行本地代码的入口尽量复用同一段创建记录的代码。这是待讨论的实现建议，不要求现在建立常驻服务。

以飞书入口为例：本人提交需要保存的内容；Hermes 取得消息中实际可用的文字和附件信息；Skill 调用保存程序，传入当前库、原始输入及入口信息；保存程序创建标准记录并返回实际笔记路径；Agent 据此报告本机保存结果；FNS 按已配置的范围同步；工作台读取同步到本机的笔记。

职责建议：

1. **入口**取得本人这次提交的文字、链接或文件，并保留实际可取得的消息位置。
2. **Agent 与 Skill**在需要理解对话时识别要保存的内容，保留原始输入，调用保存程序；AI 归纳单独记录。
3. **保存程序**检查记录笔记的目标是否属于当前库，为程序创建的记录生成标识和目录，写入 Markdown／属性，并返回成功路径或失败原因；附件位置另按第 5 节的设置与明确指令决定。手动模板不依赖这段程序。普通保存不创建 Task、不启动研究。
4. **工作台**读取这些笔记，显示记录及整理状态，不按录入入口建立多个独立 Inbox。
5. **FNS**负责已配置范围内的同步；写入方只在确认写入完成后报告“已保存”，不能据此声称另一台设备已同步。

Web Clipper、手动模板等入口可能直接由 Obsidian 保存，不一定能调用同一段代码。共同规范约束记录如何被识别、正文和状态如何保存，不强制所有入口采用相同目录结构；手动笔记不因缺少程序生成的标识而成为异常记录。聊天平台重发同一条消息时，接入程序可以利用实际取得的消息 ID 防止重建；同一链接被本人再次保存不自动当成重复消息。

## 3. 一次输入的完整流程

以“看视频时，想留下一个片段和自己的想法”为例：

1. 本人在已选定的输入入口提交视频链接、时间位置及自由文字。输入入口只把实际获得的内容交给保存程序，不编造标题、作者或摘要。
2. 由程序保存时，在当前库的 Inbox 范围内创建记录目录与主笔记，填写创建时间、该时间所用时区及“待整理”状态，把当时输入写进 Markdown 正文。由本人手动保存时，直接在 `收件箱/` 新建 Markdown，应用模板后书写，由 Obsidian 保存；不增加先建目录、生成 ID 或调用 Agent 的步骤。若使用 Agent 整理，应保留原话，AI 归纳另写。
3. 如果只是保存链接，流程到此即可。需要下载和解析时，另由本人明确决定投入，并按已确认的 Task 规则执行；原视频长期保存在库外。
4. 工作台读取记录笔记的属性，显示待整理列表；选择条目后读取正文，在详情中显示来源与自己的记录。本人或 Agent 修改笔记后，界面重新读取同一份文件。
5. 本人阅读后，可以只保留原记录、补充自己的想法、关联既有课程／Project／Task，或者按需形成独立笔记。只有明确决定投入，才创建或关联要执行的 Task。
6. 本人标记，或明确授权 Agent 标记时，才将原记录改为已整理；允许明确授权某批记录一起更新。AI 完成摘要、补充来源或视频解析本身不触发这一变化。原文件继续保留，工作台默认列表不再显示它，可以从“已整理／全部记录”找回，也可以恢复待整理。

第 02 项已用 Obsidian 插件和 `inbox.js` 实现工作台文字保存与重新读取；补充、整理及其他入口仍按后续任务实现。上述完整流程不表示每一步已交付，HTML 原型仍只有内存数据。

## 4. 已确认：手动单文件与程序条目文件夹并存

Q36 确认两种正常保存方式。本人在 Obsidian 中直接新建文件，不需要遵循程序／Skill 创建整组文件的步骤。

```text
收件箱/
├── 多个 Agent 会话切换的想法.md     # 本人新建文件 → 应用模板 → 书写
├── 读文章时想到的问题.md             # 同样是正常记录
└── 2026-10/
    └── <记录标识>-<简短标题>/        # 程序／Skill 创建
        ├── 记录.md
        └── 源文件位置.md            # 有库外原文件时按需创建
```

附件位置不固定在上述条目目录内。Obsidian 或保存程序按当前附件设置决定位置；本人向 Agent 明确指定位置时，按该指令保存。具体流程见第 5 节。

- 手动笔记的文件名由本人决定，不要求固定叫 `记录.md`，不要求本人生成 UUID 或流水号；应用模板后即可正常使用。
- 程序／Skill 保留按月分组、每条记录一个文件夹的结构。目录中的标识由程序生成，用于避免同名覆盖；不据此要求手动笔记也有相同目录或 ID。
- 工作台展示的是记录笔记，两种结构进入同一份列表。不能以固定目录深度、文件夹是否存在或文件名是否为 `记录.md` 作为唯一识别依据。
- 手动笔记后续增加附件、由 Agent 补充或标为已整理，均不自动转成条目文件夹。移动既有内容仍需本人明确决定。
- 按月分组只方便浏览和控制程序条目的目录数量，不代表按月移动或删除；手动笔记不因跨月而改变位置。
- 原视频、课程大文件等继续保存在库外，多个电脑、外置硬盘或网盘位置视为同一套内容的替代入口，不增加版本或完整度管理。手动单文件在正文增加“源文件位置”段落登记多个位置；程序记录可以保留独立位置说明文件。
- 已在课程、Project 或 Task 中保存的材料，用当前库内的链接引用，不复制整份资料。解析任务生成的完整转写及实际选用截图继续随 Task 保留。
- Inbox 不是临时文件目录，不设置自动清理。解析步骤需要的临时文件仍放在对应 Project／Task 内的 `tmp/`。
- 单文件规则只适用于 Inbox。Task 固定有独立文件夹的决定保持成立。
- 本节记录已确认的结构。第 02 项已创建程序条目目录并完成真实写入，未修改 FNS 配置；手动模板已由第 03 项接入；附件仍待后续任务实施。

## 5. 共同模板与工作台读写设计

沿用“Markdown 是可独立阅读的原记录，少量 YAML 属性供界面读取”的已有模式，避免另设一份需要人工维护的 JSON 清单。Q38 已确认共同模板的基本信息，并补充所用时区；两种结构都可被工作台识别，不要求手动 ID。下列四个核心属性已用于第 02 项程序保存，已在第 03 项安装为手动模板；程序附加字段见正式保存规范。

### 最小手动模板

```markdown
---
type: inbox
inbox_status: pending
created: "{{date:YYYY-MM-DD HH:mm:ss}}"
created_timezone: "{{date:Z}}"
---

```

本人将上述属性作为模板插入当前笔记，再自由书写正文；不必生成标识或创建额外目录。模板自动填写创建时间和所用时区。这里的时间是应用模板、初始化记录时的时间；不是文章来源的发布时间，也不会自动追溯更早的文件创建时刻。

`created_timezone` 记录该时间当时的 UTC 偏移，例如 `+08:00` 或 `-07:00`；它不是城市或地区名称。此格式能用核心 Templates 自动填写，满足区分北京时间与其他时区记录的需要，不在模板中写死北京时间或当前电脑的偏移。带夏令时的设备按记录当时的偏移保存，不能在之后读取时套用新的偏移。

工作台读取 `created` 与 `created_timezone` 后，将两者组合成明确时刻再比较、排序；不能仅比较各笔记的本地钟面时间，也不能把缺少时区的时间直接当成北京时间、UTC 或阅读设备时区。换电脑阅读、同步、补充内容及修改整理状态不重算原创建时间和时区。Q40 已确认：列表默认换算成当前阅读设备的时区，明确显示时区；详情同时保留原始创建时间和偏移。所有记录按实际时刻排序，显示换算不修改笔记。

[Obsidian 核心 Templates 文档](https://help.obsidian.md/plugins/templates#Template%20variables)允许 date/time 使用 Moment 格式串；[Moment 格式说明](https://momentjs.com/docs/#/displaying/format/)中的 `Z` 输出 `±HH:mm`。以上模板保留引号，避免属性编辑把模板变量误解析。第 03 项已在当前 Obsidian 核心模板窗口实际插入，时间与偏移均正确展开，见正式验收记录。

核心模板没有已文档化的 IANA 时区名称变量，例如自动输出 `America/Los_Angeles`。若将来需要地区时区名称，应另行设计字段与获取方式；不能从 `-07:00` 唯一反推出某个地区。当前格式用于记录历史时刻，不用于未来日程的夏令时计算。

新记录应包含类型、整理状态、创建时间及所用时区。尚未应用模板或历史记录缺少时间／时区时仍可阅读，并显示缺失提示；不补造时间、不让条目消失，不声称能够准确排定这些记录的时间顺序。`id`、录入入口、关联对象仍可选，缺少 ID 的手动笔记是正常记录；纯读取不补写任何属性。

程序／Skill 保存记录时，应读取实际写入环境的时间与偏移，从同一个时刻生成两个字段；本人明确指定其他时区时，把时间转换成该时区并记录相应偏移，不能只换时区标签而不换时间。远程 Agent 不能把服务器时区冒充本人电脑的时区；没有明确指定时，记录的是实际执行写入的环境。第 02 项已为工作台实现此时间记录，并用可选的 `source_urls` 保存用户提交的链接；来源发布时间等扩展字段仍需与条目创建时间分开设计。

正文可以只是一句话，也可以按需增加原始输入、来源与材料、自己的补充、AI 归纳等部分。不为填满模板强制生成内容；AI 归纳须与本人原话和来源内容区分。库内链接先使用笔记链接，不要求本人维护一套 ID 引用表。

### 已确认：附件默认遵循 Obsidian 设置，明确指令优先

本节约束当前库 Inbox 的附件写入。附件与记录通过正文链接关联，工作台不能以固定的附件目录来推断归属。

1. 本人在 Obsidian 中添加普通附件时，由 Obsidian 按当时设置保存。
2. 本人通过 Agent 提交附件时，Agent 先检查本次指令是否明确指定了位置。有明确要求时按要求保存；没有时，保存程序读取目标库适用的 Obsidian 附件规则，结合目标笔记位置计算存放位置，不硬编码 `attachments/`。
3. 保存程序完成实际写入后，把真实位置的链接写入记录并返回保存结果。目标不可访问或规则无法读取时，应报告具体原因，不静默改存其他目录或声称已成功保存。
4. 明确位置要求按其指令范围生效；仅指定本次附件位置不等于要求改动 Obsidian 默认设置，也不自动移动既有附件。笔记仍保留原位置。

已核对的当前配置与能力：

- 当前 `.obsidian/app.json` 中的 `attachmentFolderPath` 为 `./attachments`；这只是本次读取的设置值，不作为永久存放规则，本轮没有修改该配置。

## 8. 用具体输入检查方案

- 只有一句自己的想法：应当能保存，无须外部链接、领域或项目。
- 在 `收件箱/` 新建任意名称的 Markdown 并应用模板：正常显示，无须先创建文件夹或取得 ID。
- 尚未应用模板的手动笔记：可阅读并提示补模板，不自动移动或补写。
- 两台电脑以不同时区创建记录：分别保存本地时间及当时 UTC 偏移；读取时组合解析，不直接比较本地时间字符串。
- 阅读设备从北京时间切换到其他时区：列表换算显示并标明时区，详情中的原始值保持不变；记录的先后顺序保持一致。
- 历史笔记缺少时区：提示缺失，不默认按北京时间或当前阅读设备时区解释。
- 一条手动笔记与一条程序创建的嵌套记录：出现在同一收件箱列表；源文件位置说明不重复成为条目。
- 手动笔记增加小附件：默认按 Obsidian 设置保存并链接，原笔记位置保持不变。
- 本人在 Agent 中指定附件目录：按指定目录保存并写入实际位置，不改 Obsidian 的默认设置。
- 本人修改 Obsidian 附件设置：之后的默认写入读取新规则，不迁移已有附件，也不继续套用写死的旧路径。
- 只粘贴一个 URL：应当先保存，不强制抓取、解析或填写理由。
- 一个想法引用两篇文章：允许一条记录包含两份来源，不强行拆开。
- 同一视频又产生新想法：可以补充原记录，也可以保留新的输入上下文；系统只提示可能重复。

- Agent 仅完成视频摘要：保持原整理状态；只有本人明确要求标记时才改变。
