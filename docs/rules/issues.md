# 当前库的开发 Issue

本文中的 `<运行目录>` 按[本机运行记录](writing-and-changes.md#本机运行记录)解析，默认 `.system/.workbench-runtime/`；自定义位置从所属实例的 `.system/workbench/runtime.jsonc` 读取。

适用范围：明确开发根目录中的开发事项。工作台设置 `developmentRoot` 时以该目录为准；独立 Issue CLI 的 `--vault` 同样必须显式指向该开发根。本人、工作台与获授权的 Agent 读写同一份本地 Markdown；业务 Project／Task 继续使用各自说明笔记与状态。

## 文件与标识

- 一个功能一个目录：`.scratch/<功能名>/`；规格使用 `spec.md`，实施 Issue 使用 `issues/<NN>-<名称>.md`。
- 编号在功能内从 01 开始、递增分配。跨功能引用必须包含功能名，例如 `vault-workspace-v1#13`。同一功能不能出现重复编号。
- 修改标题不自动改文件名。关闭、重开和标为重复均保留原文件；第一版不提供移动或删除。
- 规格、任务拆分总览、backlog 不自动作为 Issue 计数。只有规格的功能仍在功能列表显示。
- `.scratch/` 是正式开发记录，不是临时缓存。本机保存成功不证明 FNS 或另一台设备已经同步。

## 普通实施 Issue 的格式

属性在一级标题前，采用独立的 `字段: 值` 行。正文从一级标题开始；评论位于 `## Comments`，之后的 `## Activity` 保存操作历史。不另建可编辑的状态数据库。

| 字段 | 语义与允许值 |
| --- | --- |
| `State` | `open`：未关闭；`completed`：已关闭且已完成；`not-planned`：已关闭且不计划实施。一个字段同时确定是否关闭及关闭结果，不能组成互相矛盾的值 |
| `Status` | 独立分诊结果，见下表；关闭不覆盖已有分诊。分诊不表示执行完成或 Agent 正在运行 |
| `Labels` | JSON 字符串数组，例如 `["缺陷", "文档"]` |
| `Priority` | `high`、`medium`、`low` 或空值；显示高、中、低或未设置 |
| `Blocked by` | 前置 Issue 完整标识的 JSON 数组，例如 `["vault-workspace-v1#06"]` |
| `Related` | Issue、功能说明及允许的开发文档的库内路径 JSON 数组 |
| `Duplicate of` | 重复记录对应的原 Issue 完整标识；只适用于 `State: not-planned`，重开时清除 |
| `Created`、`Updated` | 含时区的 ISO 时间。页面按当前设备时区显示；旧文件缺失时显示未记录，不用文件修改时间冒充创建时间 |
| `ID`、`Input hash` | 创建请求标识及原始创建参数摘要，用于识别重试；维护已有 Issue 时保留 |

没有 `State` 的旧记录显示“关闭状态待确认”，在“未关闭”列表也可找到。只读不补属性，不根据正文关键词或勾选比例推断完成。未知属性和未编辑的正文保留。

| 分诊结果 | 页面含义 |
| --- | --- |
| `needs-triage` | 待评估 |
| `needs-info` | 待补充信息 |
| `ready-for-agent` | 需求明确，可交给 Agent；执行仍取决于实际授权及前置条件 |
| `ready-for-human` | 需人工实施 |

新 Issue 初始为 `State: open`、`Status: needs-triage`。旧 `wontfix` 在明确迁移时转为 `State: not-planned`，删除该旧分诊值，不补造此前的分诊结果。技能要求“wontfix”时，执行关闭为不计划实施并记录原因。规格中的已有 `Status` 仍可用于分诊，不因规格出现状态而把它计作 Issue。

## 操作语义

- 新建只建立记录，不启动 Agent。新功能可先只有 Issue，不强制生成没有内容的规格。
- 正文支持 Markdown 和验收清单；代码块中的示例不参与验收计数。勾选与关闭分别执行；关闭时提示未勾选项及未完成依赖，由本人核对并提交关闭结果。
- 分诊、标签、优先级、关联与关闭状态分别保存。评论不能暗中变更状态，重开不自动清空验收项。
- 所有前置都明确完成才解除阻塞。目标缺失、状态未确认或关闭为不计划实施都不能当作完成；需要本人修订依赖或决定后续方案。拒绝自我依赖、循环依赖和不存在的目标。
- `Related` 可指向当前库的 Issue，功能目录内的 `spec.md`、`map.md`、`ticket-plan.md`、`backlog.md`，以及 `docs/workbench/`、`docs/rules/`、`docs/adr/` 下的 Markdown／JSON。普通业务入口仍不读取 `.scratch/`。
- 复制 Agent 上下文重新读取当前文件和前置状态，包含规则入口与真实路径；不启动、停止或监控 Agent。

## 评论与历史

旧 `## Comments` 内容原样保留，不猜测作者、日期或评论边界。新增评论采用以下标记，正文仍可直接阅读：

```markdown
<!-- tannt-comment:{"id":"唯一标识","author":"本人","created":"2026-10-21T21:00:00.000Z"} -->
评论正文。
<!-- /tannt-comment -->
```

编辑新格式评论保留 `id`、原作者和创建时间，增加 `updated`。作者是写入方提供的记录；当前库没有多人登录身份认证。UI 默认记为本人，Agent 工具默认记为 Agent，不据此认定具体会话身份。

工作台的状态、属性、正文、清单和评论修改在 `## Activity` 追加时间、操作者和具体动作；关闭结论同时保存为评论。直接编辑文件的历史不会被补造。保留标题和评论标记不能作为普通描述；保存前须闭合 Markdown 代码块，避免吞入后续管理段落。

## 决策任务

`Type: research/prototype/grilling/task` 表示既有 wayfinding 决策任务。其 `Status` 继续表示执行状态，`claimed` 为认领、`resolved` 为完成，`Blocked by` 继续使用原有编号格式；普通实施 Issue 的关闭和分诊菜单不改写它。答案、总览更新与任务选择步骤见 [Agent Issue 流程](../agents/issue-tracker.md)。

## 保存与多入口修改

工作台从当前库文件系统直接发现和读取允许范围的文件。提交时携带编辑开始时的完整原文，核对当前版本、保存变更，再读回文件，页面展示实际结果。拒绝路径越界和符号链接。

同一台电脑的工作台和 `scripts/workbench/issue-request.cjs` 共用 `<运行目录>/issues/write.lock`，串行分配编号及检查依赖。Agent 优先使用该命令执行已获授权的写入；其他文件工具仍可使用，但须遵守本规则、核对原文并避免同时修改同一文件。

每次保存会在 `<运行目录>/issues/operations/<标识>/` 保留原始版本、拟写版本及结果，用于失败恢复；由工作台或命令写入，由维护者读取，不作为另一份可编辑业务状态，保留到本人明确清理。锁仅在一次写入期间存在，正常结束即释放；异常退出遗留锁时，先核对锁中进程和操作结果，再由维护者恢复。

原文已变化时拒绝陈旧提交并保留输入。原文核对与文件替换无法为不遵守锁的外部编辑器或跨设备同步提供事务保证；恢复材料用于核对，不能宣称任意并发修改绝不会丢失。双电脑 FNS 与自动合并不属于第一版验收。

本机 FNS 已排除 `<运行目录>/`，该目录须保持 Git 忽略。初始化、接入 Git 或换设备时，须先核验忽略与同步排除。UI 尚未提交的草稿只在当前视图保留，关闭视图或重载插件前先保存。
