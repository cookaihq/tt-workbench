# 项目与任务

Project 与 Task 的概念见[术语表](../../GLOSSARY.md)。每个 Task 必须归属一个 Project；已决定投入但暂时找不到合适业务项目的任务，可由专门容纳此类工作的项目承接，项目名称按实际需要确定。每个 Task 都有独立文件夹，即使只有一份笔记。旧独立任务依获授权清单确认归属并迁移，不因目录改名丢弃原材料或重建身份。

项目表示本人已决定投入推进且范围明确的工作，可面向有限交付，也可承载长期研究或运营；只有明确终点时才记录项目整体完成条件。领域维护持续责任、标准与运行记录，资源保存知识和材料；单纯围绕主题积累不自动建立项目。项目可以包含或引用索引，不要求另建同名专题。正式工作组织保持项目与任务两层，下一步行动在任务内维护，不建立子项目层。

## 目录与说明

项目集中存放，领域可选，项目间按需平级关联，见[ADR 0004](../adr/0004-project-centered-information-architecture.md)。领域、客户和创作方向通过链接或关联表达，不作为项目的物理父目录。

| 对象 | 路径 |
| --- | --- |
| Project（含研究、运营、课程开发和企业交付） | `1.项目/<项目名>/项目说明.md` |
| 项目内 Task | `<Project目录>/任务/<任务名>/任务说明.md` |
| 已归档 Project 与其 Task | `4.存档/项目/<项目名>/` 中保留项目整包及内部任务关系，原路径见归档记录 |

项目说明保存范围、推进目的、当前重点与任务入口；任务说明保存具体工作、完成条件、进展和下一步行动。背景、执行过程、来源和结果按实际需要增加，不为填满模板预建空文件。工作台从实际说明文件读取状态，存档中的任务继续保持项目归属。

创建 Project 提供名称、范围与推进目的，不要求预先选择领域。新建 Task 须选择所属 Project，提供名称与预期结果，并明确怎样判断完成；完成条件可在预期结果正文中表达，不要求单独字段。任务允许包含多个步骤、跨多次会话。两者初始为“待开始”。创建记录或关联来源不启动 Agent。账号事实信息属于对象资源，不作创作方向。实际创建入口及验证状态见[项目任务实现](../workbench/work-records.md)，旧入口的限制不改变本规则。

## 任务资料归属

任务目录集中保存为该任务取得或产生的原始输入、会话、研究记录、附件与结果；本人或获授权的 Agent 在这里补充研究，工作台读取同一批文件。任务暂停、完成或归档时，专属资料仍随任务保留。

- 本人明确从 Inbox 创建任务或将输入归入已有任务时，迁入完整原记录及其专属附件。可以按原记录标题设资料子目录，允许多条输入归入同一任务；任务说明链接实际资料位置。
- 原输入成为任务内的来源笔记，保留正文、原身份、创建时间、来源及整理状态。迁移可将其类型改为普通笔记，并记录原路径与原类型；这是明确的迁移操作，普通更新不能改类型。新任务的身份和创建时间独立生成。
- 迁移前核对范围、共享引用、目标重名及当前原文。目标文件读回、附件字节和链接核验后，才移除收件箱中的源文件；失败明确报告已完成步骤与恢复位置，不重复建任务或覆盖他人修改。
- 迁移同时更新库内业务笔记的真实链接与附件路径；外部网页、库外原文件、历史会话正文不因迁移被改写。原始附件保持字节，不能自动改写其中的历史记录。
- 已有独立归属、供多项任务共用的课程或通用资料保留主要位置，各任务引用。不能把其他记录仍依赖的文件擅自认定为专属附件；归属不明确时先报告具体文件和引用者，再决定迁移范围。
- 后续新增的任务专属附件保存到该任务内，见[附件规则](attachments.md)。库外长期大文件仍按该规则登记位置，不因本规则强制搬入库。
- 迁移范围包含网盘托管文件或托管替代文件时，必须先按[网盘托管规则](cloud-files.md)由 `tt-cloud-files` 处理路径联动，再核验整项资料迁移；普通文件复制不能代替网盘移动和替代记录更新。

## 状态与属性

Project 为 `type: project`，Task 为 `type: task`；两者使用 `title`、`status`、`created`、`created_timezone`、`id`。时间与偏移在同一时刻生成。Task 另外有字符串属性 `progress` 与 `next_step`；进度写明已完成内容、当前问题和下一步。归属由实际目录表达，不另建一份可编辑归属字段。

| 编码 | 显示 | 含义 |
| --- | --- | --- |
| `not_started` | 待开始 | 已决定投入，尚未开始 |
| `in_progress` | 进行中 | 正在推进 |
| `paused` | 暂停 | 暂停推进，保留继续可能 |
| `completed` | 已完成 | 约定目标已达到 |
| `cancelled` | 已取消 | 已决定不继续，保留记录，不计为完成 |

本人、明确获授权的 Agent 与工作台读写同一份说明笔记属性，不另建业务状态数据库。Project 与 Task 状态分别维护，Task 完成不自动结束 Project。业务状态不是 Agent 正在运行的证据。读取不补字段；未知或缺失状态提示核对。

日期与等待信息按需记录，沿用上述五种状态。遇到等待时说明等待对象、条件与下次检查时间；承诺的截止时间和本人计划推进的日期分别表达，不强制每项工作填写日期。具体可查询字段及相应界面仍待实现。

仍在 Inbox 的共享输入可以用 `related_work` 保存指向项目或任务说明的引用；这仅表达引用，不代表迁移完成。迁入任务的来源笔记由任务说明链接，其 `capture_origin` 保存原路径、原类型和迁移时间；保留的 `inbox_status` 仅为原整理状态，不再参与收件箱列表。其他来源在正文中链接。追加或状态更新遵守[写入规则](writing-and-changes.md)，保留无关属性和正文。

工作状态与存放位置分别表达：完成、取消或暂停不自动归档；明确归档时按[存档与恢复](scope-and-directories.md#存档与恢复)整包移动项目及其任务，不单独搬走任务形成无项目归属的记录。归档保留原工作状态，恢复也不自动把已完成任务改为进行中。可分别查看活跃、暂停、已结束和已归档工作；共用资源不因单个项目结束而退出使用。

开工时选择当前重点任务；每周短回顾收件箱和投入中的项目，检查下一项任务、卡点及范围变化，不强制日记或重看全部知识。临时文件与长期材料分别按[附件规则](attachments.md)处理。功能开发 issue 使用 `.scratch/` 和其分诊状态，不使用业务 Task 的五种状态。
