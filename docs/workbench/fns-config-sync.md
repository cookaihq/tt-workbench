# 工作台 FNS 配置同步

从左侧「系统 → FNS 配置同步」或命令面板「tannt 工作台：打开 FNS 配置同步」进入。页面采用 C「差异工作区」，展示本机与最近接收的权威版本。共同语义见[发布与应用规则](../rules/fns-config-sync.md)。

## 使用流程

1. 在每台设备先安装并完成 FNS 本机设置，准备当前库的 Git `origin` 及本机凭证助手。程序不会新建远端或替换凭据。
2. 打开「设备检查」。`0.21.0` 起，插件目录里的普通配置直接可用。旧链接点击「迁回本机配置」：程序暂停 FNS、保存恢复材料，将完整配置原样迁回插件目录，核验后清理本机旧源并恢复原启用状态。身份、路径或内容冲突须先处理；不再创建符号链接。
3. 在来源设备的 FNS 设置中修改四组规则，回到工作台点击「发布本机配置」。核对本机与远端差异，确认发布并推送。
4. 在另一设备点击「检查更新」，按四组查看增删差异，选择「比较并应用」。本机有未发布修改时，确认会替换这些修改；取消可保留本机并准备发布。
5. 查看写入与加载结果。已接收不表示已应用；已应用也不代表网络服务已完成文件传输。

推送失败时可重试同一版本；远端争用时先检查更新，再选择是否放弃原待推送记录并重新发布。上次应用的恢复入口会核对当前内容，发现之后的改动则停止，保留恢复材料。

## 每条规则的设置说明

`0.20.0` 起，权威版本每条规则右侧显示设置原因；尚未填写的显示「暂无说明」。点击对应行的「填写／编辑」，或顶部「编辑说明」，为本机规则填写目的、原因或适用条件。说明为纯文本，每条最多 4000 字。

「保存说明草稿」保存到本机，左侧显示草稿，右侧继续显示已发布版本。通过「发布本机配置」核对规则和说明变化后，确认发布新版本；只改说明也可以发布。其他设备更新到支持说明的工作台后，点击「检查更新」即可看到对应版本的说明，无需先应用规则。旧工作台无法读取新格式发布，须先更新工作台。

编辑失败保留输入；「稍后继续」只保留当前视图中的未保存输入，关闭视图或重载前须保存。保存后草稿重开仍在。发生并发变化时，点击「重新比较」，对照当前权威说明核对后再保存；不会直接用新版本依据重试旧输入。收到新发布时，已保存的旧版草稿也须核对后重新保存，才能发布。

说明按字段组、规则模式和大小写选项匹配；删除的规则不把说明传给其他条目。规则正文仍由 FNS 设置维护，说明不改变任何同步行为。

## Git 与本机数据

完整运行配置位于 `<Obsidian 配置目录>/plugins/fast-note-sync/data.json`，作为普通文件排除 Git。发布时读取其原文，在传输提交中生成 `config/fns-config/<设备标识>/data.json` 固定快照；该路径无需存在于当前工作目录。发布使用 `origin` 的独立分支 `tannt-fns-config`，与普通工作分支独立；不要把它合并到工作分支或改作整库分支。

一次发布对象只包含来源设备完整配置快照和 `config/fns-config/authority.jsonc`。接收读取 Git 对象，不 checkout、不改用户索引，不把收到的完整文件覆盖到本机。版本记录中的指纹只覆盖四组规则。

本机记录保存在 `apps/workbench/data/fns-sync/`，包括最近接收记录、待推送记录、应用回执及 `operations/<标识>/` 恢复材料。备份含本机完整配置，保持 Git 忽略、FNS 排除和本机访问权限，不复制为其他设备的运行记录。回执绑定设备身份和 Obsidian 配置目录。明确恢复时程序会核对遗留锁的进程已经退出；活进程、权限不足、记录损坏或后续配置变化均停止，保留现场。

说明草稿在 `state.json` 的 `notesDraft` 中；发布后写入专用分支 `authority.jsonc` 的 `notes`。发布格式 `schema: 2` 增加说明，仍读取 `schema: 1` 的历史版本。每条说明用 `field`、`pattern`、`caseSensitive` 对应规则，正文为 `reason`；规则指纹继续仅覆盖四组 FNS 规则。

已知远端内容损坏、指纹不符或历史断裂时，最近收到的版本只供回查，不能继续应用旧缓存绕过异常。须维护者先修复传输分支，再重新「检查更新」。普通网络失败不清除已接收内容，也不把检查时间伪装成最新成功时间。

## 独立程序入口

`node scripts/fns/sync-request.cjs` 从 stdin 读取 JSON，输出不含凭据的 JSON。读取检查不要求工作台运行。

```json
{"action":"check"}
```

支持 `receive`、`preview`、`publish`、`apply`、`retry`、`discard`、`onboard`、`recover`。`preview` 使用 `kind: "publish"` 或 `kind: "apply"`，发布和应用必须原样传回对应 `plan`。`discard` 传待推送的 `publicationId`，`recover` 传上次操作的 `operationId`。自定义 Obsidian 配置目录通过 `configDir` 传入。`onboard` 仅迁回已知本机旧链接；普通文件无需接入，不会外移或建链。

维护说明先调用 `check`，使用返回的 `notes.expected` 作为原样依据，再调用 `save-notes`，传 `expected` 和完整 `notes` 数组；清空数组表示清除本机规则的全部说明。示例条目：`{"field":"configSyncOtherDirs","pattern":".scratch","caseSensitive":false,"reason":"填写实际设置原因"}`。缺省说明可从 `notes.entries` 读取后局部修改，不能省略其他条目造成误删。保存说明不需要暂停 FNS，也不会发布；发布使用通常的预览与确认入口。

独立程序需要写本机配置时，必须先在 Obsidian 中实际停用 FNS，再传 `fnsStopped: true`。程序同时核对磁盘启用列表，保持停用状态；完成后手动启用并在工作台核验。此确认不是运行时控制证明，不能仅编辑启用列表来绕过暂停。

## 当前边界

- 规则编码和运行时行为核验基于 FNS 2.4.0；其他版本写操作会停止，需先复核兼容性。
- 白名单校验需证明不会覆盖设备配置与恢复目录。无法证明范围的复杂表达式会阻断操作，提示改用明确目录；不会自动删改规则。
- 没有记录时显示「内容一致」；实际 FNS 未加载或加载值不同，会保留「已写入、待加载核验」。界面不监控其他电脑。
- Windows 不再要求为 FNS 创建符号链接；身份、文件替换与 FNS 实际加载仍须原生验证。macOS 夹具不能替代 Windows 实机验证。
- 实施与验收状态见[规格](../../.scratch/fns-config-sync/spec.md)及[实现验收](../../local-evidence/.scratch/fns-config-sync/verification/implementation.md)。
