# 工作台收件箱实现

业务规则正文见 [收件箱规则](../rules/inbox.md)，写入与冲突要求见 [写入规则](../rules/writing-and-changes.md)。本页只说明工作台如何实现它们。

`main.js` 收集表单标题、正文和来源；`apps/workbench/inbox.js` 调用 `lib/vault/` 的共用创建模块。模块生成时间、属性和可读目录，以独占创建写入 `记录.md`，读回后返回实际路径。`request_hash` 是实现用的请求摘要，配合 `id` 判断重复提交，不作为另一份业务状态。

同名记录按真实目录占用增加序号。表单未修改时复用原请求，修改输入后生成新请求。失败保留当前视图输入；收起仅隐藏表单，关闭视图不持久保存尚未落盘的草稿。

文件由 Obsidian 监听后进入列表，工作台读取真实元数据与正文；尚未发现文件时保留已保存路径并提示稍后读取，不重复创建。`lib/vault/catalog.js` 综合类型、附件设置和主笔记登记的附件路径识别记录，读取不修改原文件。

详情的追加与状态更新通过 `note-editor.js` 调用独立文件模块，保留创建时间、未知字段与正文。冲突返回辅助笔记路径；放弃表单重新读取只丢弃当前表单输入，不删除已落盘冲突文件。

收件箱使用 `0.收件箱/`。分流可将原记录和专属材料迁入项目、任务、领域或资源，工具和实际边界见[文件操作说明](../agents/vault-file-operations.md#分流到项目领域或资源)；旧 `reviewed` 状态不代表已完成分流。普通保存、摘要或添加引用均不自动启动工作。

历史第 02—04 项证据见 [验收索引](../../local-evidence/docs/workbench/verification/README.md)，独立文件模块此前结果见[原实施任务](../../.scratch/vault-rules-and-skills/spec.md)。五目录与扩展分流的新证据见[信息架构实施记录](../../.scratch/information-architecture-workflow/spec.md)，不以旧版本验证替代。
