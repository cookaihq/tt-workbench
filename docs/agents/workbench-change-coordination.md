# 工作台与目标库的变更联动

适用条件：设计或修改工作台的规则、共同概念、文件格式、Skill、模板、CLI、读写或展示行为，或者接收目标库对此类内容的变更交接。开始设计与修改前读取本文；实现中发现新影响时复查。本文路径相对于工作台根，目标库路径另行标注。

## 确认归属与依据

1. 读取本项目 `AGENTS.md`、[领域文档约定](domain.md)、相关 `docs/rules/`、ADR 和实际调用方；维护术语及决定时遵循领域文档。操作目标库时先按[软件位置与目标库规则读取](package-layout.md#目标库规则读取)核对其实际入口、概念和适用规则。
2. 区分产品通用能力、共同模型与实例选择。工作台在自己的 `docs/rules/`、`docs/agents/`、`GLOSSARY.md`、`docs/adr/` 保留所需正文；目标库在自己的项目内维护所需正文。每个项目内部同一含义一处正式正文，跨项目可各自独立使用；共同含义变化须检查另一方，不能用跨项目去重删掉使用方规则。
3. 按目标受众检验产品方案。某个使用者的分类、网盘目录、集成选择或个人工作习惯，只约束该实例；成为产品默认值需有适用依据和明确决定。个人全局正文归所选规则源，工作台只维护读取、整理和接入工具。

完成条件：能说明本次预期行为、软件与目标库分别负责的正文、已确认决定、实际实现与未验证项。已确认范围直接执行；新冲突展示双方出处、影响及可行处理，不默默覆盖目标库规则。

## 检查并实施关联变更

逐项核对规则和术语、字段与目录格式、Skill 的主题触发及读取路径、模板、CLI、工作台读写／展示、规则页面、初始化、打包、安装和更新。检查调用方原有用途与既有笔记兼容；说明无需改动的依据。Markdown 修改本身不会改变程序能力。

在已有授权内同步修改受影响的正式源与实现；安装副本由正常打包安装生成。目标库有并行维护会话时，明确分工、交付文件及验收责任，通过交付记录提出需配套修改的具体文件和含义，保留其修改。库外项目根由本机已确认的项目登记或用户路径定位，共享文档使用各自根的相对路径，不要求固定相邻位置。

目标库变化影响软件时，按交接范围完成软件修改及验证；软件变化影响目标库时，在已授权范围更新并验收，超出范围的具体修改留在协调记录。tannt 的反向入口为其项目根的 `docs/agents/workbench-change-coordination.md`。工作台开发规格与 Issue 使用本仓 `.scratch/` 及[开发跟踪流程](issue-tracker.md)，不推广到目标库业务 Project／Task。业务笔记迁移须有明确范围，规则或版本更新本身不授权迁移。

## 验收与交付

按实际变化测试受影响入口；需要交付软件时执行项目要求的测试、构建和正常安装，在明确目标库核对版本、文件哈希及安装后读取链。安装、业务初始化、Skill 注册和个人规则接入分别处理，不能互为隐式副作用。

从 Agent 的实际入口核对触发条件、逐级路径及执行要求；分别记录文本／路径检查、程序行为、宿主新会话发现与加载、其他设备到达情况。规则冲突或实现尚不支持时保留现场，列出具体缺口，不能把旧验收或局部通过当作整体完成。

交付记录保存到本仓 `.scratch/<功能>/`，列出改动、共同含义对应关系、测试／构建／安装结果、授权外协调项和未完成验证。向使用方说明两个根目录下需保持的相对路径；其他设备根目录可不同，但对应入口与引用关系也须保持。
