# Domain Docs

## Layout

本仓库采用 single-context，整个软件仓库共用：

- `GLOSSARY.md`：领域术语及其定义。
- `docs/adr/`：长期架构和组织方式的决策记录。

这里维护软件所需概念；目标库在自己的项目内维护所需概念。两边共同含义变化时按[工作台变更联动](workbench-change-coordination.md)检查对应定义，项目内部保持一处正文，跨项目允许各自独立使用。业务 Project／Task 与软件开发 Issue 分别遵守所属规则。

## Before exploring, read these

先阅读根目录的 `GLOSSARY.md`，再阅读与当前任务有关的 ADR。
同时遵守项目 Agent 规则，查阅相关设计、研究和验证文档；
项目经验不只记录在 ADR 中。

术语表或 ADR 不存在时，直接继续，不提示缺失，
也不为了初始化而建议创建空文件。
`/domain-modeling` 在术语或决策实际确定后按需创建这些文件。

## Use and revisit the glossary's vocabulary

术语表记录本仓库当前的领域共识。执行已确定范围内的任务时，
任务标题、方案、假设和测试名称使用既定名称，避免随意引入同义词。

探索、规划或讨论概念边界时，先检查现有定义是否能表达用户当前的目标。
出现以下任一情况，应主动重新审视相关术语、内容分类及目录用途约定：

- 用户明确要求讨论或调整已有定义。
- 当前目标、新事实或具体案例无法被现有定义准确表达。
- 现有定义排除了用户希望积累或使用的内容，或与相关概念产生难以解释的重叠。

此时按以下顺序推进：

1. 说明用户希望得到的结果，以及现有定义限制了哪些合理内容或选择；
   不因文档已有定义，就先把这些内容排除出讨论。
2. 提出具体的新定义或边界调整，说明依据、取舍，以及对相关概念、
   目录用途和既有内容归属的影响。新概念也先检查能否通过修订现有术语表达。
3. 区分已经确认的修订与仍待讨论的提案。需要用户取舍时给出推荐；
   已有明确授权和结论时，按该结论更新，不重复要求确认。
4. 定义确定后，通过 `/domain-modeling` 更新 `GLOSSARY.md`，
   并检查 `README.md`、`AGENTS.md` 及相关说明中的重复、冲突和路径引用，
   按已确认范围同步修改。目标知识库既有笔记是否需要调整，依据实际影响另行确定。

用户已明确要求重新讨论的定义，在本次探索中属于待修订的前提；
不能继续用它否决修订方向，也不能把尚未确定的新定义写成已确认规则。

## Flag ADR conflicts

方案与现有 ADR 冲突时，明确指出相关文件、冲突内容
和建议重新讨论的理由，不静默覆盖已有决定。
