# 工作台独立仓库迁移方案

## 目标与已确认范围

将工作台及其配套实现的正式源码迁至 `D:\zhao\tt-workbench`，作为未来公开的独立 Git 仓库。继续以桌面 Obsidian 插件交付，允许安装到不同名称和位置的知识库，沿用现有五目录及项目／任务格式。本轮做通独立打包、测试和指定知识库安装；GitHub 地址及首次线上发布稍后设置。

用户已确认完整范围：所有工作台相关内容，包括共同规则、Agent 规则、可复用模板、Skill 和开发材料一起迁移。全局主指令及五个场景也作为独立全局规则源迁入新仓。插件安装仅放入插件与内置资源，后续初始化、配置、Skill 注册或全局规则接入由安装后的页面操作触发。更新采用公开 GitHub 发布版本提示，用户点击后下载安装。

用户已确认 Q1—Q5：共用程序一起迁移，新仓从当前代码建立新的 Git 历史，过去提交留在 tannt 回查；同时明确将当前项目全部 Skill 源码纳入工作台仓库。决定依据见 [ADR 0005](../../docs/adr/0005-independent-workbench-repository.md)，问答与事实见[讨论记录](map.md)。

新增的 [Skill 安装 UI](../workbench-skill-installation/spec.md) 在代码迁移完成后再梳理需求、制作原型并请用户确认。当前阶段只处理源码归属和维持现有使用所必需的安装能力，不提前确定该 UI 的功能与交互。

源码按现有相对结构迁移：`apps/workbench/`（排除 `data/`）、三个 `lib/` 子目录、五个活动 Skill 及清单、六个 `scripts/` 子目录（`agent-skills`、`cloud-files`、`fns`、`global-agent-instructions`、`vault`、`workbench`），另含根级 `scripts/fns-hidden-audit.mjs` 及其测试。

- `scripts/workbench/migrate-numbered-roots.cjs`
- `scripts/workbench/verify-numbered-roots.cjs`
- `scripts/vault/migrate-para.cjs`

这些脚本绑定旧业务结构、迁移清单或当时授权，不成为新库初始化动作。`scripts/fns/env-sync-support.mjs` 仍被隐藏项审计和测试依赖，属于必须迁移的复用实现，不能按旧脚本遗漏。

调查时的自动化测试为 19 个文件，分布在工作台、三个共享模块、网盘脚本、FNS 脚本及隐藏项审计。完整保留 YAML 2.9.1、JSONC parser 3.3.1 的随附代码、来源记录与许可证；实施时以实际文件重新核对。

- `.scratch/` 中工作台、Skill、共享模块及规则开发记录随迁。含真实笔记副本、设备配置或恢复材料的原始验收数据作为新目录内不纳入 Git 的本地证据保存；公开的规格、测试与结论保持对应关系，不把旧证据当作新安装已通过。

- 新仓与 tannt 的 `AGENTS.md`／`CLAUDE.md` 分别维护各自项目入口。引用已迁规则时解析正式源或安装资源，规则正文不双份维护。既有历史断链单列缺项。

迁移以实际文件清单与内容哈希为准，包含当前已存在的未提交 Skill 实现；不以旧 Git 提交代替工作区最新内容。实施前再次检查并行修改，发现源文件变化时重新核对对应项，不覆盖其他会话结果。

新仓保留清楚的程序、共享模块、工具、Skill 和文档边界。目标知识库使用完整安装产物，日常运行不依赖新仓位于某台电脑的固定绝对路径。独立 CLI 直接访问目标库文件，不要求 Obsidian 进程或工作台接口运行。

## 迁仓必须接续的现有行为

- 安装器接受明确的目标库，安装位置按实际 Obsidian 配置目录定位；解除固定库名 `tannt` 的限制。
- 插件、笔记读写、开发 Issue、剪藏、FNS 工具、网盘工具与各 Skill 使用同一个明确目标库，不能把新源码仓库误当业务库。
- 网盘授权档案是否位于库内，按实际目标知识库判断；程序迁仓不移动凭据或扩大读取范围。
- 现有 Codex、Claude 项目级 Skill 发现入口核验旧目标后迁接到安装产物；这是本次迁仓独立的维护步骤，不并入普通插件安装。保留显式宿主选择和只读检查；标准发现、文件可读及实际执行分别验证。
- 工作台及 CLI 继续共用目标库的锁、回执和恢复记录。新源码仓库不承接各知识库的运行状态。
- 保留现有插件身份，接续原有用户设置。仅在目标文件和引用已核验、安装与必要回归通过后移除原正式源码。
- 更新原库的 Agent 入口、执行文档和命令引用，指向新的正式源或已安装工具；不维护两份可编辑的程序或 Skill 正文。

## 实施与切换顺序

1. 确认完整方案，生成源／目标明细、版本与恢复记录。必要备份统一置于 `D:\zhao\tmp\tt-workbench-migration-<时间戳>\`，完成后报告实际路径。
2. 在新目录准备完整源码与本地 Git 仓库，修改源码定位、目标库参数、模块引用及打包安装入口。保持原库可用，先完成新副本的检查。
3. 运行适用模块和脚本测试，在名称不同、路径不同的隔离知识库验证独立安装及 CLI；安装产物的运行不依赖 tannt 源码目录。
4. 核对原库最新版本，将安装产物更新到 tannt，接续现有 Skill 发现入口，验证受影响的真实使用入口及运行记录一致性。
5. 核对目标和引用后移除原正式源码，保留 Q6 明确的知识库材料与本机运行记录。更新规则入口和安装说明，核查 Git 忽略与本机 FNS 适用排除规则。
6. 在新仓保存迁移结果、尚未验证的平台与实际证据；形成当前源码的起始提交，不配置或推送未知 GitHub 远端。随后进入已登记的 Skill 安装 UI 需求与原型阶段。
