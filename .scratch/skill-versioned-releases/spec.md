# Skill 独立版本与批次发布

依据：2026-10-31 用户完整交接，已确认需求见本机交接材料。本记录固定软件实现契约，不把示例 tag、候选版本或本地构建当作正式发布。

## 已确认的结果

每项 Skill 使用独立行为版本；调用时报告本次加载的名称与版本，页面读取同一份 `SKILL.md` 元数据。2026-10-31 用户补充确认：工作台和 Skill 同次更新时共用 `v<工作台版本>` Tag；仅 Skill 更新使用 `skills-YYYYMMDD.N`，不包含单个 Skill 名称。每批包含完整正式版本清单，仅选定的变更项产生包，其余项逐字继承上批固定来源。检查逐项比较版本、兼容性和校验值；失败保持当前可用内容，不显示“最新”。仅 Skill 发布不占 GitHub Latest；联合发布沿用工作台 Latest 策略。

## 实现边界与选择

- 唯一版本源：`skills/<名称>/SKILL.md` 的字符串 `metadata.version`。首次引入独立版本以 `1.0.0` 作为本地候选基线，不表示已经发布；后续各项单独升版。兼容字段与更新说明同在该元数据中，由发布清单生成器读取。
- 分发单位：每个 Skill 的安装目录自带 `runtime/`，包含同一源码快照的共用工具和引用文档。比依赖随工作台变化的共享运行时多占磁盘，但版本能覆盖实际行为，Obsidian 关闭后仍可运行。源码仍只有一份共用实现，分发副本由构建生成。
- 保持发现位置：Codex `.agents/skills/<名称>`、Claude Code `.claude/skills/<名称>` 继续相对指向插件 `skills/<名称>`。目录中的 `skill-package.json` 登记包内哈希；独立更新整体切换该目录，两个已注册宿主采用同一磁盘版本。页面分别检查发现入口；旧会话缓存不能由磁盘结果推断。
- 管理归属：工作台 `release.json` 声明其交付的 Skill 包。升级时验证独立包自身完整性，保留已存在的独立包（即使新工作台附带版本不同），核心资源继续按原工作台清单校验。旧无版本目录先按旧清单完整验证，在引入新模型的工作台升级中转为有版本初始包；后续不再随工作台升降版。插件安装不注册发现入口、不写目标库规则或服务配置。
- 兼容旧用户文件：包内未受管理的配置保留；与新包重名且内容不同则保留原状态并给出可操作结果。受管理内容确有用户修改时不默默覆盖，正常正式更新更新管理清单，不产生伪造的 LOCAL_CHANGES。
- 恢复与并发：独立更新与工作台更新共享插件安装锁。下载/完整校验先于切换；在插件恢复目录保留原包与操作记录。正常失败恢复旧目录；进程中断由明确恢复入口核对阶段与哈希后续做或回退，不抢占活进程锁，不覆盖外部变化。
- 批次清单：schema、kind、repository、batch、sequence（首批 1、逐批加 1）、previous（上批 Tag 与清单内容摘要）、active 名称集合及逐项版本、内容摘要、包 SHA-256/字节数/固定 Release tag 与附件名、兼容要求、更新说明。两类 Tag 共用一条继承链，对完整集合、来源和版本严格验证。
- 发布：基于指定上批正式清单，显式选项构建；同名同版本不同内容被阻止，未选项不读取开发正文。受同一串行发布流程协调，联合发布先构建 Skill 清单和包，再从它们组装工作台三个附件；全部上传同一草稿，下载核验并复查基线后一次公开。仅 Skill 发布 `make_latest=false`，联合发布 `true`。本地构建不上传、不推送。CI 使用短期 GitHub Actions 身份，不读取个人 Token。
- 发现：分页读取正式 Release 列表，工作台按合法工作台版本选择；Skill 接受两类 Tag 下的清单，按序号及完整继承链核验先后，再逐项比较行为版本。不含清单的纯工作台发布跳过；清单损坏时保留可用清单并提示检查不完整，继承链分叉时停止判定。两者均不依赖全仓 latest。

## 关联范围

保留安装器/CLI/UI 共用逻辑、Git/FNS 隔离、运行目录解析和文件保护。Skill 资源位于现有插件排除范围；恢复沿用插件恢复范围，不新增用户必须配置的同步目录。配置/笔记运行记录仍归目标库。联动安装、更新、构建与发布说明、软件位置规则、发布设计文档场景及目标库使用说明；既有未提交修改逐段保留。

## 验收

1. 多项选择、完整继承、联合与独立发布交替、跨批次更新、重复版本变化、缺附件、清单不完整、继承链分叉、并发基线变化；联合发布工作台三个附件与同一 Skill 清单一致。
2. 网络/限流/预算耗尽、兼容不足、校验失败均保留旧内容；更新说明、安装/可用版本与按钮状态准确。
3. 两类更新的两种顺序、旧链接/无注册/损坏/同名冲突、双宿主、用户文件保留、故障及中断恢复。
4. 从隔离安装副本执行配套 CLI；真实页面与宿主新会话验证名称/版本提示。结构、文件、发现、实际调用分别记录。
5. `npm test`、`npm run build` 和必要隔离验证。未公开发布、未正式安装 tannt 或未验证的设备/宿主分别列明，不用候选试装替代正式采用。
