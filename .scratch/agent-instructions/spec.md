# Agent Instructions Skill 规划

状态：访谈中，未进入实现。开始于 2026-10-31。

本记录区分用户已明确的目标、当前实现事实与待决定的方案。讨论采用 grill-with-docs 的分轮访谈与领域建模方式；确定的术语按需进入根目录 `GLOSSARY.md`，具有长期取舍的架构决定按需进入 `docs/adr/`。

## 用户已明确的目标

- 新增 Skill，稳定调用名为 `agent-instructions`，展示名使用 Agent Instructions。
- 面向任意用户；运行不要求 Obsidian、工作台或指定知识库。用户个人规则可作为使用案例，不作为通用前提。
- 覆盖全局指令与项目指令的新建、增补、审查冲突、拆分整理和读取入口修复。
- 用户显式选择安装此 Skill 时，默认安装到所选 Agent 的用户级位置；独立入口与工作台入口采用同一默认范围。安装工作台本身不自动安装此 Skill。宿主范围仍待确定。
- 新 Skill 开发完成后，`skills/tt-organize-agent-rules` 下线退役。
- 当前任务是规划，先形成共同理解；不据此执行 Skill 实现、安装或旧 Skill 退役。

## 已有约束与术语

- Skill 正式源码归本仓库；安装副本通过分发流程生成。个人规则正文归用户选择的规则源，不随公共软件包分发，见 [ADR 0005](../../docs/adr/0005-independent-workbench-repository.md)。
- 现有项目约定是插件安装只写插件目录；Skill 注册及全局规则接入分别由明确操作完成。第一轮已确认沿用此边界。
- 沿用 [术语表](../../GLOSSARY.md) 中的“全局主指令”和“全局场景指令”。Skill 安装范围、规则适用范围及 Agent 读取规则的入口分别讨论，不能从“全局安装”推导为“只能维护全局规则”。
- 本记录中的项目文件路径以本仓库根为基准；Markdown 链接以本文件目录为基准。本记录不确立用户设备上的新目录布局。

## 分轮决定与设计树

第一轮于 2026-10-31 获用户回复“采用推荐”，三项均已确定，不重复询问：

| 问题 | 已确认决定 | 后续设计分支 |
| --- | --- | --- |
| Q1 使用者与独立性 | 面向任意用户，脱离 Obsidian、工作台和指定知识库运行；个人规则是案例。 | 通用原则与个人约定的边界、独立分发资源、规则组织方式。 |
| Q2 首版职责 | 全局与项目指令全流程维护，包括新建、增补、审查、整理和入口修复。 | 触发条件、日常修改与整体整理、规则归属、验收场景。 |
| Q3 默认全局安装 | 用户显式安装 Skill 时默认所选宿主用户级位置；工作台安装本身不触发。 | 宿主与系统、自定义配置位置、多个来源冲突、更新卸载、旧项目入口退出。 |

已确定的产品与依赖边界记录在 [ADR 0006](../../docs/adr/0006-standalone-agent-instructions-skill.md)。后续方案尚未确认；宿主能力、文件和调用方等环境事实由 Agent 查证。

沿用当前授权原则：具体要求及会话内已确认的决定持续有效；普通编辑不机械增加审批轮次。仅当范围、条款含义、去向或行为改变仍有实质分歧时，提出具体取舍。安装 Skill 不自动授权修改用户规则或连接其他宿主。

### 第二轮：待用户决定

本轮问题已提出，以下推荐尚未视为已接受：

| 问题 | 推荐 | 主要影响与替代路径 |
| --- | --- | --- |
| Q4 规则组织 | 优先沿用用户既有且有效的布局；新建或明确整理时推荐简短主指令与按需场景。目录遵循用户已有约定，不强制五份个人规则。 | 固定布局便于工具识别，但强制迁移会扩大日常编辑的范围，也不适合已有项目约定。 |
| Q5 多宿主的共同要求 | 用户希望多个 Agent 共同遵守的要求只维护一份正式正文；宿主入口分别适配，差异单独表达；现有多份正文先比较后决定合并。 | 多份独立正文容易分别漂移；单一正式源需要明确其位置、入口能力和源不可用时的处理。 |
| Q6 触发与沉淀 | 用户表达维护长期指令或修复其读取入口的意图时可自然语言触发；为完成已授权任务而维护规则时同样适用。普通纠正先用于当前任务，长期沉淀可以提出建议，已有保存授权直接沿用。 | 自动从普通纠正中提炼并保存会把当前任务要求扩展为以后适用的行为，须由用户选择是否纳入产品范围。 |
| Q7 首版宿主与系统 | 正式支持 Codex、Claude Code，以及 macOS、Windows 原生环境；各组合分别验证新 Skill 的全局安装、规则加载与业务结果。 | 这两个宿主有较完整的项目实现和历史证据；其他宿主需要查证自己的入口、触发和加载机制。用户仍可明确首版增加的目标。 |

Q7 在独立事实调查返回后加入本轮；它不依赖 Q4—Q6 的选择。规则源的具体默认位置与新用户初始化安排依赖 Q4、Q5 的答案；不提前写定目录布局。

### 后续选择所需事实

- 本仓当前实现明确支持 Codex、Claude Code；历史新会话证据证明当时的项目级发现与调用，不证明新 Skill 的全局安装。当前 macOS 会话列出了用户级技能目录中的 Skill，也不能据此推广到所有宿主与版本。
- 现有项目约定覆盖 macOS、Windows 原生；WSL 作为独立环境，Hermes 另行接入。WorkBuddy 5.8.3 有项目 `AGENTS.md` 候选加载器的静态检查记录，尚无本仓全局指令及 Skill 集成的实际验证。
- 规则页读取器支持绝对 `CODEX_HOME`、`CLAUDE_CONFIG_DIR`，有本仓夹具测试；全局规则安装器却拒绝自定义目录。这属于现有安装器限制，不能解释为宿主能力限制。Skill CLI 的 `--config-dir` 指 Obsidian 配置目录，不是 Agent 配置目录。
- 本轮未取得可引用的新增官方宿主规范正文；实现前仍须核对各目标宿主当前版本的发现、触发和规则加载机制。
- 本机个人全局主指令已要求：维护全局／项目规则与读取入口时，读取规则维护场景。该场景包含完整维护流程；规则源 README 另有旧规则整理迁移流程，并引用插件中的旧 Skill。公共新 Skill 的流程与这些个人约定应分清职责；退役旧 Skill 本身不会消除这些外部入口。
- 相邻能力分别有独立职责：`tt-sync-agent-config` 检查运行环境和服务配置，明确排除规则整理；Skill 创建和安装由对应工具处理；Git 等业务 Skill 可能在完成其任务时调用规则维护能力。模型、凭据、MCP 与命令执行权限配置不能仅因也称为“Agent 配置／规则”就归入本 Skill；写入文字指令也不等于部署了 hooks 等执行拦截。

## 退役必须覆盖的关联项

这些是已发现的实现依赖，具体迁移策略待设计收敛：

- 新 Skill 对旧 Skill 必需职责的覆盖，以及独立使用所需资源。
- 活动清单、名称映射、展示文案、调用提示词、规则页发现检查和安装说明。
- 用户规则源 README 中已发现的旧 Skill 活动引用；以及新全流程职责与既有规则维护场景的重叠。公共 Skill 开发和用户规则源的修改是不同操作范围，本规划不据此提前改写个人规则。
- 打包目录以及已安装的 `tt-organize-agent-rules`、更早的 `tannt-organize-agent-rules` 项目入口。
- 旧入口的归属核对、清理或迁接方法；不能仅凭同名删除用户自有内容。
- 新入口可发现、可调用并完成相应业务之后的退出顺序；中断后的处理与恢复依据。
- 分别验证独立安装、工作台入口、受支持宿主和系统，以及真实行为；结构检查与历史验收不能代替这些结果。
