# tannt 信息架构与工作流重构方案

当前方案依据用户最新指定的五个业务根目录：`0.收件箱/`、`1.项目/`、`2.领域/`、`3.资源/`、`4.存档/`。采用 PARA 组织宏观管理职责，融合卡片盒写作与连接；库根首页及按需 MOC 承担导航。此结构取代此前的目录候选，不设独立任务、导航或待考虑根目录。

用户已明确“按照这个方案执行”，接受 Q22 保留长期项目的适配 PARA 与 Q23 明确实体归档，并授权实施本方案。规则、代码、365 个文件迁移、工作台 0.17.0 正式安装、原生入口及本机 FNS 恢复核验均已完成；第二台设备尚未验证。当前结果以文末实施记录为准。

确认历史见[讨论地图](map.md)，决策背景见[ADR 0004](../../docs/adr/0004-project-centered-information-architecture.md)，当前术语见[根术语表](../../GLOSSARY.md)。正式规则集中于 `docs/rules/`；本方案记录设计依据、实施范围与验收结果，不作为另一份现行规则正文。

## 已接受的约束

- 推进工作为第一优先，同时容纳学习、思考、未成熟观点和无明确用途的积累。
- 正式工作保持项目—任务两层，每个任务必须属于一个项目。找不到业务归属的已决定工作，可由专门项目承接；不把未决定投入的想法变成任务。
- 长期研究、持续运营也可成为项目，项目必须有清晰范围和投入承诺；Q22 已再次确认这一选择。
- 任务有可判断的完成条件，可多步骤、多会话；下一步行动放在任务内部。
- 项目集中存放，通过链接关联领域、客户、创作方向及其他平级项目；不增加子项目层，不强制每个项目填写领域。
- 输出是工作流概念。项目、任务及其他成果按各自需求组织，不建立全库成果总览、统一成果登记结构或强制成果文件夹。
- 内容可暂时没有用途；有多项用途时分别记录、查看、更新，并回查实际使用版本。通用内容演进不覆盖历史交付。
- 经验与知识共同组织，同时保留个人实践背景、适用条件和证据。原文、AI 归纳、本人判断分别识别。
- 卡片与 MOC 按需形成，不要求所有材料原子化，不预建主题树。不同创作方向通常分别建项目，也允许实际需要下的跨方向、跨账号关联。
- 沿用五种工作状态，日期与等待按需记录；开工选重点、每周短回顾，不自动创建提醒或日历。

## 方法依据与适配

[PARA 作者原文](https://fortelabs.com/blog/para/)将项目描述为积极推进、有目标的短期工作，领域为持续责任，资源为感兴趣或学习中的主题材料，存档为前三者不再活跃的内容。原文存档例子包括完成或搁置的项目，因此“完成”和“存档”不能简单等同。

[Zettelkasten.de 总览](https://zettelkasten.de/overview/)强调聚焦的笔记、未来仍可理解的表达、可引用身份及有意义的连接。双向链接和标签只是手段；“PARA + Zettelkasten 是目前最主流的进化方向”没有本轮可核验的流行程度证据。本方案的依据是符合本人推进工作与积累认识的需要。

本轮采用适配后的 PARA：保留长期项目，以“决定推进的工作”区别于领域的“持续维护责任”。曾比较的严格 PARA 方案会把无结束条件的长期责任移入领域，把研究阶段设为有限项目；用户通过 Q22 选择保留 Q1/Q8 中已确认的长期项目，不采用该替代方案。

卡片盒中的 note archive 是长期知识集合，不等于 PARA 的历史存档。仍在使用的知识卡片不因名称中出现 archive 就进入 `4.存档/`。

## 五个目录的定义

| 目录 | 管理职责与进入条件 | 典型内容 | 边界 |
| --- | --- | --- | --- |
| `0.收件箱/` | 承接尚未澄清如何处理、主要归属未定的输入 | 临时想法、待判断的链接与原始输入 | 澄清不等于研究透彻；知道放哪里即可分流，明确归属时可直接保存到目标 |
| `1.项目/` | 组织本人已决定投入推进、具有明确范围的工作 | 研究、课程开发、具体培训交付、内容制作及其任务、过程、结果 | 允许长期项目，但必须能说明当前推进问题；不是任何主题资料的容器 |
| `2.领域/` | 维护本人持续承担的责任、运行标准与跨项目管理信息 | 培训业务质量要求、客户关系维护、账号运营定位与复盘 | 领域不是所有兴趣或学科分类，也不是项目的父目录；执行工作仍通过项目—任务推进 |
| `3.资源/` | 积累可独立维护、供理解、判断和工作使用的知识与材料 | 知识与经验、来源资料、对象档案、可复用讲义模板、已澄清但未承诺的想法 | 不要求已被多个项目使用；项目专属原件不因被引用就自动搬走 |
| `4.存档/` | 保留明确退出当前工作或维护范围、仍有回查价值的上下文 | 退出活跃集合的项目、停止承担的领域、明确退役的资源版本或集合 | 不是垃圾箱、备份、所有旧文件或全部历史经验；通过明确操作整包迁移并可恢复 |

### 项目、领域、资源的判定

先看内容在管理什么，而不是看主题或时间长短：

- 项目回答“我决定推进哪件工作，现在推进什么？”；领域回答“我持续对什么负责，需要维持什么标准？”；资源回答“我需要保留什么认识、事实和材料？”
- “AI”只是内容主题。AI 资料与观点可在资源中；持续承担 AI 教学能力建设的责任可形成领域；决定研究某种教学方法的具体问题可建立项目。
- 长期运营项目与领域不能重复维护定位、质量标准、复盘结论或状态。领域保存持续有效的要求，项目记录投入推进的范围、任务与变化，双方链接。
- 领域的管理记录可保存在领域内，但动作仍归入项目中的任务。周期性维护可由范围明确的运营项目承接；这是保留长期项目的一项实际用途。
- 客户背景资料可在资源维护；持续跟进客户关系的管理记录可在领域维护；本次培训需求、定制、交付属于项目。一个文件同时涉及多方面时按主要维护用途选一处，其他入口引用。

“没有当前项目时仍需我负责维持”有助于识别领域；“即使不承担这项责任，这份认识或材料仍值得参考”有助于识别资源。两者都可能长期存在，持续时间不能决定归属。

### 名称与导航

正式集合名称统一为“资源”，承接此前广义“资料”；“资料”保留为日常用语，不再表示另一平级实体。“来源资料”继续表示来源及其上下文这一子类。该术语调整与领域定义已同步术语表。

根首页负责选择工作与快速进入内容；MOC 是按需要编写的主题索引，可以跨五个目录连接内容，不复制正文和状态。领域页可包含导航，但还承担责任和标准的正文。原[导航临时示例](../../tmp/information-architecture-workflow/navigation-example/README.md)展示的是旧候选布局，不能作为新目录清单使用。

以下仅示意，子目录按实际需要建立，不预建空分类：

```text
首页.md
0.收件箱/
1.项目/
    <项目名>/
        项目说明.md
        任务/<任务名>/任务说明.md
        ……项目所需的过程、材料与成果
2.领域/
    <责任领域>/领域说明.md
3.资源/
    知识/             # 认识与经验共同组织
    来源/             # 课程、文章、视频等来源包
    对象/             # 公司、客户、账号等事实档案
    可复用内容/        # 持续维护的讲义、案例、模板等
    专题/             # 按需 MOC，不复制被引用正文
4.存档/
    项目/<项目名>/     # 示例，明确整包归档及恢复
    领域/<领域名>/
    资源/<退役集合>/
```

未承诺的想法可作为普通资源笔记或相关主题中的一段保存，无须重新建立“待考虑”分类或强制状态。后续决定投入时，创建或关联项目任务并链接原想法，不改写过去的承诺状态。

这些是业务内容根目录；源码、规则、Skill、模板、开发记录和运行数据继续按工程职责保存在现有位置，不把 `docs/`、`apps/`、`lib/`、`skills/`、`.scratch/` 等整体塞入 PARA。

## 输入、推进与结果使用

1. 收集：归属不明时进入收件箱；归属明确时直接保存至目标。
2. 澄清：判断内容是什么、是否已决定投入、主要保存在哪里。澄清后的输入实际分流，不能只从列表隐藏。
3. 推进：项目维护范围、目的和当前重点；任务记录完成条件、进展与下一步。日常从任务中选重点，周回顾检查收件箱、当前项目及卡点。
4. 积累：有独立维护价值的认识提炼到资源，通过链接保留项目过程和原始来源；不强制每个任务产出卡片。
5. 使用：成果在所属项目、任务或内容自身上下文组织。计划或实际用途按需要就近记录，多项用途各自更新，关联实际版本。
6. 退出当前集合：按已接受的明确操作规则归档；来源、知识和通用内容是否继续使用分别判断。

沿用待开始、进行中、暂停、已完成、已取消五种工作状态。归档表示是否仍在当前管理集合，不是第六种工作结果；已取消项目也可被存档，已完成任务仍可保留在进行中的项目内。领域归档不自动归档其所有关联项目，项目归档也不自动归档被其引用的资源。

任务完成不自动结束项目；长期项目定期说明本阶段正在回答的问题和下一项可完成任务，不用虚构项目最终完成时间。等待记录说明对象、条件及再看时机；承诺截止与计划日期区分，不强制所有记录填日期。

原输入身份、原文、来源及创建时间保留；派生项目或任务有自己的身份，不把原件保存时间充当投入承诺时间。实体归档的整包迁移仍须保持工作身份、任务所属关系与历史用途可追溯。

## 卡片盒与 MOC 如何落实

- 来源笔记保留出处、摘录和随来源形成的学习记录；知识笔记围绕可独立理解的问题或观点，用自己的表述说明认识、依据和不确定性。可以从真实需要开始，不设数量、字数或成熟度流水线。
- 经验卡片注明实践情境、实际结果、条件和证据。AI 帮忙归纳不自动成为本人结论，更不等于本人已经实践。
- 连接说明关系：例如支持、反驳、适用条件、因果或延伸问题。只堆相关链接或标签，不能替代对关系的说明。
- MOC 提供围绕主题的阅读路线、当前认识和未解决问题；标签用于少量跨主题检索维度，不再复制一套文件夹分类树。无需为每个主题同时建立领域、项目与 MOC。
- 长期复用的知识在资源内保持相对稳定的主要位置。项目中的临时分析与领域的运行记录就地保存；形成独立认识后再提炼并链接，避免因每次使用而频繁搬家。
- 连接可以跨目录：项目的发现连接资源中的观点，经验连接存档中的原始证据。可引用身份应在改名、搬迁、归档后继续可追溯；是否需要额外 ID 字段属于实现设计，当前不强制时间戳命名。

## 更值得优先解决的问题

1. 内容的主要归属和链接复用：同一份内容只能有一个主要维护位置。领域、项目和 MOC 的多视角不意味着多份正文。
2. 项目与领域的管理分工：领域负责持续标准，项目负责推进，避免每次复盘两份状态和两套目标。长期项目至少能指出当前推进内容，不能变成永久占位的主题名。
3. 存档的含义与粒度：退出当前管理集合和知识过时是不同问题；知识的有效性、版本与替代关系应表达在内容中。进行中的项目内已完成任务不应因为完成就被拆出去。
4. 真正的知识加工：区分来源、AI 归纳、本人判断和实践证据；相关链接说明为什么相关。是否增加链接由理解和使用需要决定。
5. 能否找回和重新开始：归档后仍可检索、追溯和恢复；资源中的反向链接仍指向实际项目、任务和证据。
6. 维护成本：既定每日选重点、每周短回顾先跑通；不为五个目录各建一套重复台账，也不要求每周审阅全库。
7. 迁移是否改变工作含义：真实工作、验收样例、平台镜像和历史交付分别处理；目录迁移不能推断完成、取消、个人认可或远端发布。

## 协调回退与恢复范围

`node scripts/vault/migrate-para.cjs rollback` 只回退本次迁移清单管理的业务快照，不能单独恢复整个系统。它依据 `apps/workbench/data/para-migration/manifest.json` 核对迁移后内容，将 `before/` 中的原业务文件复制回旧位置，恢复清单中的根文件引用编辑，再移除对应迁移目标和脚本新增的两个承接项目说明。目标或新增项目发生修改时会拒绝回退；不能通过改写清单或覆盖用户新内容强行绕过。

以下对象不在该命令的自动回退范围：本轮另外新增的首页及分类导航、飞书各空间的 `latest.json` 与新本地映射、FNS 配置和启停状态、代码与正式文档、已安装工作台副本，以及其他后续修改。脚本也不保证删除所有空目录，且没有自动停止 FNS 的保护；业务回退成功不等于这些对象已经一致。

需要退回旧布局时，按一个协调恢复过程处理：

1. 先停止 FNS 和其他同步、暂停工作台写入，并保留当前业务、映射、配置及安装状态。核对 `apps/workbench/data/para-migration/` 中的清单、`before/`、`after/`、`app-paused.json`、`wiki-mapping.json` 与现存文件；有迁移后新写入时先保留并明确处理，不能只恢复旧快照丢弃它们。
2. 核对可回退条件后运行业务 `rollback`。它不是多文件原子事务；若中断或报错，先按清单检查已恢复源、仍存目标及实际阶段，保留两侧内容，不能假定重复执行一定能够完成。
3. 分别核对两个飞书空间 `apps/workbench/data/lark-wiki-sync/<space_id>/runs/para-20261027T045621Z-local-mapping/previous-latest.json` 备份。业务正文和嵌入回到旧路径后，将各空间的 `latest.json` 协调指回备份所引用的旧清单和比较基准，核验节点身份、共享正文路径及哈希；保留新映射运行记录供追溯。本地回退不向飞书发送移动或删除。
4. 逐项恢复或调整导航、FNS 配置、代码文档及正式安装，使其与选定布局一致；保留并核对 FNS 配置符号链接。对迁移后新增或已修改的导航先保存版本，不直接删除。核验文件、引用、插件读取与同步排除后再恢复同步。

本轮 FNS 已将 363 条旧路径退役至服务端回收站，恢复前还须核对 `fns-retirement/` 报告及回流备份，将服务端回收记录与本地业务清单一起处理，不能只执行本地 `rollback` 就重新启动同步。当前回收站记录是可找回依据，不表示已经实测从服务端还原，也不保证永久保留；恢复时须重新核对实际可用内容。
